# 上传入口改造方案

> 目标：把 bubble-ocr-app 的 `POST /upload` 从「本地同步跑 pipeline」改成「入队 → Windows 节点认领」。
> 改造点最小化，只动 bubble-ocr-app 的 `server.py`，其余不动。

## 一、现状

`bubble-ocr-app/src/bubble_ocr/server.py` 的 `_handle_upload()` 现在做的事：

1. 解析 multipart，取 `image` 字段
2. 校验文件类型（魔数）+ 图片尺寸上限
3. 存到 `data/uploads/`
4. 把 `state.image_path` 指向新图，`state.payload` 清空（结果重置）

也就是说，现在上传**不触发推理**——推理是用户在前端点「识别」按钮后，走 `/region` 或直接调 `pipeline.run` 时才发生的。上传本身只是换图。

## 二、改造目标

上传后，不是只换图，而是**把图纸提交给推理队列**：

```
客户浏览器 上传图纸
    ↓
POST /upload（bubble-ocr 现有入口）
    ↓
[改造点] 存图 + 转发给推理队列服务
    ↓
POST /api/inference/upload（队列服务，存图 + 建 pending 任务）
    ↓
Windows 节点 claim → 下载 → YOLO+OCR+VLM → 回传 result.json
    ↓
队列服务 status=done，前端轮询拿到结果
```

## 三、两种做法（推荐 A）

### 做法 A（推荐）：bubble-ocr 上传后「转发」给队列服务

bubble-ocr-app 保持现状，只在 `_handle_upload` 末尾加一步：把刚存的图**转发**给推理队列服务（内网 HTTP 调用）。

```python
# _handle_upload() 里，存图成功后追加：
def _enqueue_inference(dest: Path):
    """把图纸转发给推理队列服务，创建 pending 任务。"""
    import urllib.request
    queue_url = os.environ.get("INFERENCE_QUEUE_URL", "http://inference:8090")
    # 重新打包成 multipart 转发（或直接传文件路径，看队列服务接口）
    boundary = secrets.token_hex(16)
    data = dest.read_bytes()
    body = (
        f"--{boundary}\r\n"
        f'Content-Disposition: form-data; name="image"; filename="{dest.name}"\r\n'
        f"Content-Type: application/octet-stream\r\n\r\n"
    ).encode() + data + f"\r\n--{boundary}--\r\n".encode()
    req = urllib.request.Request(
        f"{queue_url}/api/inference/upload",
        data=body,
        headers={
            "Content-Type": f"multipart/form-data; boundary={boundary}",
            "Authorization": f"Bearer {os.environ.get('INFERENCE_UPLOAD_TOKEN', '')}",
        },
        method="POST",
    )
    with urllib.request.urlopen(req, timeout=30) as resp:
        return json.loads(resp.read().decode())
```

**优点**：上传入口完全复用现有 bubble-ocr 的 `/upload`（SSO、校验都保留），队列服务是独立的小服务，职责清晰。这是最贴合你模块化架构的做法。

### 做法 B：把队列逻辑直接并进 bubble-ocr 的 server

在 `bubble-ocr-app/src/bubble_ocr/server.py` 里直接加 `/api/inference/claim`、`/input`、`/result` 等接口，复用同一个进程 + 同一个 sqlite。

**优点**：少一个服务、少一次内网跳转。**缺点**：bubble-ocr 变重，推理节点和上传耦合在一个服务里，不符合你「模块化」的拆分思路。

## 四、推荐架构（模块化，贴合你的平台）

新增一个独立小服务 `inference-queue`（就是本方案 `server/server.py`），挂进 compose：

```
compose.yaml:
  services:
    inference-queue:
      build: ./inference-queue
      environment:
        INFERENCE_NODE_TOKEN: <节点令牌>
        INFERENCE_UPLOAD_TOKEN: <上传令牌>
        INFERENCE_DB: /data/inference.db
        INFERENCE_STORAGE: /data/storage
      volumes:
        - inference-data:/data
      # 加入与 bubble-ocr-app、portal 相同的 docker network

    bubble-ocr-app:   # 现有，改一行：上传后转发到 inference-queue
      environment:
        INFERENCE_QUEUE_URL: http://inference-queue:8090
        INFERENCE_UPLOAD_TOKEN: <上传令牌>
```

## 五、前端结果获取

前端上传后拿不到同步结果了，改为**轮询**：

```
上传 → 拿到 job_id（来自 /api/inference/upload 的响应）
     → 前端轮询 GET /api/inference/jobs/{job_id}
     → status 变 done 后，从 result.json 渲染识别结果
```

> 注意：bubble-ocr 现有的可视化工作台（`web/index.html`）是「同步识别 + 本地渲染」模式，
> 改成异步后前端需要加一个「轮询 job_id」的环节。这是前端唯一要改的地方。

## 六、SSO 鉴权衔接

- **上传**：沿用 bubble-ocr 现有的 SSO（`BUBBLE_IDENTITY_URL`），不变。
- **节点端**（claim/input/result）：用 `INFERENCE_NODE_TOKEN`（节点身份 token），与 SSO 无关——节点不是"用户"，是"机器"。
- **前端查状态**：`GET /api/inference/jobs/{id}` 建议也走 bubble-ocr 的 SSO 或加一层鉴权，避免任何人能查别人任务（单客户场景可先放宽松，多客户必须做）。
